# ADR 0009: 種目の順序付けルールと、複合種目優先をどこに置くか

- ステータス: **Accepted**
- 日付: 2026-08-21
- 関連: design.md §5.2、§5.3、[ADR 0008](./0008-selection-objective-and-algorithm.md)、[#13](https://github.com/June3141/muscle-training-roulette/issues/13)、[#14](https://github.com/June3141/muscle-training-roulette/issues/14)

## 背景

design.md §5.3 は順序付けに 3 つのルールを挙げている。

1. compound → isolation
2. 大筋群 → 小筋群
3. 先に小筋群を潰さない

ルール 1 とルール 2 は衝突する。
小筋群を主働とする複合種目と、大筋群を主働とする単関節種目のどちらを先に置くかで答えが割れる。
三頭の JM プレスと胸のダンベルフライがその形になる。

さらに [ADR 0008](./0008-selection-objective-and-algorithm.md) は、複合種目優先を
目的関数の項として置くかを未解決のまま残していた。

決めるべきことは 2 つ。

- ルール 1 とルール 2 の優先順位。
- 複合種目優先を目的関数に置くか、順序付けに置くか。

## 決定

### 1. 大筋群優先を第 1 キー、compound 優先を第 2 キーにする

並べ替えのキーは 4 段。

1. 主働筋の大きさ（大 → 小）
2. `mechanic`（compound → それ以外）
3. 指定部位への重み合計（大 → 小）
4. `id` の昇順

### 2. ルール 3 は独立した機構として実装しない

ルール 3 はルール 1 とルール 2 の優先順位を指定しているだけで、別の並べ替えではない。

### 3. 筋の大きさは 3 段階しか持たない

大筋群・中間・小筋群。個々の筋に断面積を与えない。

### 4. 複合種目優先は目的関数から外し、順序付けにだけ置く

[ADR 0008](./0008-selection-objective-and-algorithm.md) が未解決にしていた係数 μ を 0 にする。
目的関数はカバレッジと多様性の 2 項になる。

## 理由

### なぜ大筋群優先が先か

ルール 3 の違反を「種目 X が種目 Y より前にあり、X の主働筋 M が Y の補助筋で、
かつ M が Y の主働筋より小さい」と定義すると、
**主働筋の大きさで昇順に並べた時点でこの条件は成立しえない。**
X が先に来るなら X の主働筋は Y の主働筋以上の大きさだからである。

無作為な 6 種目 20000 組で数えると、`mechanic` を第 1 キーにした場合は
1.7% の組（違反ペア 380 件）で「小筋群を先に潰す」並びが出る。
大筋群を第 1 キーにすると 0 件になる。

**この 0 件は測定結果ではなく定義上の帰結である。**
ルール 3 の定義そのものが「小さい筋の種目を先に置くな」なので、
大きい順に並べれば自動的に満たされる。
測定が示しているのは 0 件になることではなく、逆順にすると 1.7% 壊れるという方の数字。

頻出する違反はどれも同じ形をしている。

```
Standing Barbell Press Behind Neck [compound/三頭] → Dumbbell Flyes [isolation/大胸筋中下部]
JM Press                           [compound/三頭] → Dumbbell Flyes [isolation/大胸筋中下部]
Dips - Triceps Version             [compound/三頭] → Dumbbell Flyes [isolation/大胸筋中下部]
```

### なぜ筋の大きさを 3 段階にとどめるか

断面積を持ち込むと「上腕三頭筋と三角筋のどちらが大きいか」の議論になるが、
順序付けに要るのは「先に潰すと後が続かない」の判別だけで、細かくしても出力は変わらない。
重み付けと同じ方針で、収束ではなく明らかな誤りの除去を目的に据える。

### なぜ複合種目優先を目的関数から外すか

選択時に効かせると単関節種目が候補から押し出される。

μ = 0.1 と μ = 0 で実データを解いた結果:

| ケース | μ = 0.1 | μ = 0 |
|---|---|---|
| `ppl_push` | 複合 6 / 単関節 0 | 複合 4 / 単関節 2 |
| `ppl_pull` | 複合 5 / 単関節 1 | 複合 4 / 単関節 2 |
| `chest_only` | 複合 4 / 単関節 1 | 複合 3 / 単関節 2 |

μ = 0.1 の `ppl_push` には三頭の単関節種目が 1 件も含まれない。
**[#14](https://github.com/June3141/muscle-training-roulette/issues/14) の完了条件
「`ppl_push` ケースで三頭の単関節種目がプレス系より後に来る」が原理的に検査できない。**

`chest_only` でも、重み 1.0 の単関節フライが重み 0.65 の複合種目に置き換わる。
胸を指定してフライが選ばれないのは §5.2 が防ごうとしていた状態そのもの。

design.md §5.2 の文言は「序盤に `compound` を**配置**しやすくする」で、
配置は §5.3 の仕事である。選択集合の中身を変える根拠になっていない。

## 影響

- design.md §5.2 の項が 2 つになり、複合種目優先が §5.3 に移る。
- `ppl_push` と `chest_only` の出力が変わる。ゴールデンセットのスナップショットは
  まだ存在しないので差分は出ないが、[#15](https://github.com/June3141/muscle-training-roulette/issues/15)
  で採るスナップショットはこの決定の後の値になる。
- 筋の大きさの 3 段階は engine が持つ。タキソノミーは解剖学上の分類で、
  「先に潰すな」はトレーニング上の方針なので、データパッケージに置かない。
- 主働筋は `muscleWeights` のキー順ではなくタキソノミーの並び順で同点を解く。
  JSON のキー順は上流の記述順で決まり、意味を持たない。

## 未解決

- 大筋群と中間の境界。三角筋と上腕三頭筋を中間に置いたが、
  上腕三頭筋を小筋群に落とすと三頭の複合種目がさらに後ろへ動く。判断材料がない。
- 同じ大きさの筋どうしの順序。胸と広背筋のどちらを先に置くかは決めていない。
  現状は指定部位への寄与と `id` で決まる。
- ルール 3 の定義に使った「補助筋」は上流の secondary をそのまま写したもので、
  精度が低い。ダンベルフライの補助筋に上腕三頭筋が入っているなど、
  実際には依存していない組が含まれる。[#17](https://github.com/June3141/muscle-training-roulette/issues/17) の重みレビューで見直す。
