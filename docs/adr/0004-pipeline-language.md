# ADR 0004: データ生成パイプラインも TypeScript で書く

- ステータス: **Accepted**
- 日付: 2026-08-17

## 背景

M1（タキソノミーへの写像）と M2（重みのベースライン生成）は、
873 件のデータを読んで変換して書き出すバッチ処理であり、
この種の作業には Python（pandas）や Rust を使う選択肢がある。

## 決定

**リポジトリに残す生成パイプラインは TypeScript で書く。**

## 理由

### 1. パイプラインは将来のアプリに引き継がれない

これが決定の中心。M1〜M2 の変換は、M5 で重みが確定したらほぼ二度と走らない使い捨てのバッチ。
将来のトレーニングアプリ（§1）が受け取るのは**成果物の JSON だけ**で、
パイプラインのコードは持っていかない。

したがって「将来のバックエンド言語に合わせておく」という動機が働かない。
パイプラインの言語は、**今このリポジトリで書きやすいもの**を選べばよい。

### 2. 生成した直後に同じスキーマで検証できる

生成側が TypeScript なら、生成物をそのまま `datasetSchema.parse()` に通せる。
Python でも JSON Schema を共有すれば同じことはできるが、
そのために 2 つ目のツールチェーンを CI に入れる価値はない。

### 3. 性能は問題にならない

873 件の変換は一瞬で終わる。選択エンジンの貪欲法も同様（§5.1 は「実装は数十行」）。
Rust の速度が要る場面がこのプロジェクトには存在しない。

### 4. CI が 1 ツールチェーンで済む

Python を足すと lint / format / typecheck / test の一式が二重になる。

## 「zod スキーマが唯一の正」ではない

**将来 DB が入れば、正はそちらに移る。**

種目データはユーザーデータではなくマスタデータなので、
DB を持つアプリでも「JSON をシードとして流し込む」形になる可能性が高い。
その時点で正はテーブル定義になり、zod スキーマは
「JSON がテーブル定義に適合しているか」の検証に格下げされる。

これは想定内で、問題にならない。引き継がれるのは JSON とその形の合意であって、
検証がどのツールで行われるかではないため。

**この ADR が主張しているのは、今このリポジトリの中で
生成と検証が同じ型定義を共有できる、という閉じた話に限る。**

## 例外

**使い捨ての探索は何で書いてもよい。**
分布を眺めるだけのアドホックな集計にスキーマの一貫性は関係ない
（`docs/data-survey.md` の数字も node のワンライナーで取っている）。

線引きは「リポジトリに残るか」。残るものは TypeScript、残さないものは自由。

## LLM レビュー（§4.4 手順 3）について

Anthropic の TypeScript SDK があるので、これも TypeScript で書ける。
バッチ処理のために Python を持ち込む理由にはならない。
