# ADR 0003: 筋肉タキソノミーの粒度と人体図 SVG の粒度衝突

- ステータス: **Accepted**
- 日付: 2026-08-17
- 関連: design.md §4.3, §8.2

## 背景

本プロジェクトのタキソノミー（§4.3）は既存データセットより細かい。

- 三角筋 → 前部 / 中部 / 後部
- 大胸筋 → 上部（鎖骨部）/ 中下部（胸肋部）

一方、流用候補の SVG（`lahaxearnaud/body-highlighter` 系、いずれも
`HichamELBSI/react-native-body-highlighter` のパスを祖先に持つ）は
`chest` / `front-deltoids` / `back-deltoids` 程度の粒度しか持たず、
**三角筋中部と大胸筋の上下分割がない。**

分割しない場合、サイドレイズとショルダープレスが同じ場所を光らせることになり、
Q1（重み付けデータは「特に効く部位」を表現できるか）の検証力が落ちる。
可視化は Q1 の主計測器（§2）なので、これは計測器の分解能の問題である。

## 選択肢

| 案  | 内容                                       | コスト                   | Q1 への影響                                      |
| --- | ------------------------------------------ | ------------------------ | ------------------------------------------------ |
| A   | SVG のパスを自前で分割する                 | 高（ベジエの手作業分割） | 分解能を保てる                                   |
| B   | SVG の粒度に合わせてタキソノミーを粗くする | 低                       | Q1 の検証が成立しなくなる                        |
| C   | データは細かいまま、SVG 表示時に合算する   | 低                       | 図では区別できないが、バーチャートでは区別できる |
| D   | 人体図をやめてバーチャートのみにする       | 最低                     | 分解能は保てるが、部位の直感的な把握を失う       |

## マッピングを作った結果

流用元（`react-body-highlighter` 2.0.5、MIT）が持つ領域は 22 個で、
うち人体の筋肉に対応するのは 19 個（残りは head / knees / neck）。
22 分類を突き合わせた結果は次の通り。

| 状態 | 分類数 | 内訳 |
|---|---|---|
| 1 対 1 で乗る | 12 | 三角筋後部、僧帽筋上部、脊柱起立筋、上腕二頭筋、上腕三頭筋、大腿四頭筋、ハムストリングス、内転筋群、下腿三頭筋、腹直筋、腹斜筋、（三角筋前部） |
| **衝突**（複数分類が 1 領域） | 9 | 下表 |
| **領域が無い** | 1 | 腹横筋 |

### 衝突は 5 箇所

| 領域 | 乗る分類 | 判断 |
|---|---|---|
| `front-deltoids` | 三角筋 前部 + **中部** | **A（分割）** |
| `chest` | 大胸筋 上部 + 中下部 | C（合算） |
| `upper-back` | 広背筋 + 僧帽筋中下部 | C（合算） |
| `forearm` | 腕橈骨筋 + 前腕屈筋群 | C（合算） |
| `gluteal` | 大臀筋 + 中臀筋 | C（合算） |

**§4.3 の警告（三角筋中部と大胸筋上下の 2 箇所）より多い。**
背中・前腕・臀部の 3 箇所は、タキソノミーを ADR 0005 で確定させたときに増えた分。

### 判明した別の問題

流用元は `abductors` という名前の領域を持つが、**座標は大腿内側**（前面 x 35-48 / 53-65、
体の正中は x=50）にあり、実体は内転筋である。名前を信じると中臀筋を内股に表示してしまう。
`packages/data/src/body-map.ts` では `adductors` として持ち、この食い違いを注記した。

中臀筋は大臀筋の深部・上外側にあり、流用元に対応する領域が無いので `gluteal` に合算する。

## 決定

**三角筋のみ A（パスを分割）、他の 4 箇所は C（表示時に合算）。腹横筋は人体図に出さない。**

分割するのは `front-deltoids` の 1 パスだけで、前部と中部に割る。

**三角筋は A（SVG のパスを分割）を前提にする。大胸筋上下は C で始める。**

三角筋を分けたい理由は Q1 の検証力そのもの。M1 の写像を実装した結果、
**317 件を前部 219 / 中部 166 / 後部 69 に振り分けられた**（重複あり）。
これだけの分解能をデータ側が持っているのに、図で合算すると
サイドレイズとショルダープレスが同じ場所を光らせることになり、
**計測器の分解能がデータより粗い**状態になる。

大胸筋の上部/中下部は C で始める。
インクライン系とフラット系の違いは種目名から明らかなので、
図で区別できなくてもバーチャートで読める。背中・前腕・臀部も同じ理由。

データ側のタキソノミーを粗くする（B）のは不可逆な損失なので採らない。

## 腹横筋を人体図に出さない

深層筋なので体表に領域が存在しない。腹直筋の領域に合算すると、
プランクとクランチが同じ場所を同じだけ光らせることになり**図が嘘をつく。**

`UNDISPLAYABLE_MUSCLES` に理由付きで置き、バーチャートだけで扱う。
領域も理由も持たない分類があるとテストが落ちるので、**黙って消えることはない。**

## 影響

- 対応表は `packages/data/src/body-map.ts`。SVG そのものは M6 で作る
- M6 で `front-deltoids` のパス分割が 1 件必要（`needsSplit` が印を持つ）
- 合算する 4 領域では、図と バーチャートで見える分解能が違う。
  **図で区別できない部位があることを UI で示す**（区別できると誤解されると Q1 の読み違いになる）

## 参考

流用元はいずれも MIT。**ライブラリとして依存せず、SVG パスだけ抽出して自前アセットにできる。**
これは §8 の「画像素材を使わず SVG を自前で持つ」判断と矛盾しない。
