# ADR（Architecture Decision Record）の運用

## 何を ADR にするか

**後から覆すのが高コストな決定だけ。**

判断基準は「その決定を変えたとき、既存のデータやコードをどれだけ書き直すことになるか」。

| 例 | ADR にするか |
|---|---|
| 重量を片側で持つか合計で持つか | **する** — 変えると全データを書き直す |
| 何を独立軸にしてよいか | **する** — スキーマの根幹 |
| 筋肉タキソノミーの分類 | **する** — 変えると全種目の写像をやり直す |
| oxlint の複雑度の閾値 | しない — いつでも変えられる。`docs/toolchain.md` に書く |
| 変数名の付け方 | しない |

**迷ったら書かない。** ADR が増えるほど、どれが生きているか分からなくなる。
ツール選定のように「調べ直すのが面倒だが変更は容易」なものは
`docs/toolchain.md` のような通常のドキュメントに書く。

## ステータス

```
Draft ──→ Proposed ──→ Accepted ──→ Superseded
                   └──→ Rejected
```

| ステータス | 意味 |
|---|---|
| `Draft` | 論点は書いたが、選択肢を絞り込めていない |
| `Proposed` | 案を 1 つに絞った。レビュー待ち |
| `Accepted` | 決定した。実装はこれに従う |
| `Rejected` | 検討したが採らなかった。**消さずに残す**（同じ検討を繰り返さないため） |
| `Superseded by ADR-XXXX` | 別の ADR に置き換わった |

## 改訂のルール

- **`Accepted` になる前は、本文を直接書き換えてよい。** 推敲の履歴を残す必要はない
- **`Accepted` になった後は、本文を書き換えない。** 決定が変わったら新しい ADR を作り、
  古い方のステータスを `Superseded by ADR-XXXX` にする

理由: `Accepted` な ADR はコードやデータが依拠している前提そのものなので、
「いつからその前提だったのか」が追えなくなると、既存データの解釈ができなくなる。

## 書き方

**決定と、その決定に至った根拠を書く。自分の推敲の経緯は書かない。**

残す価値があるのは、将来の読者が同じ検討を繰り返さずに済む情報。

- 残す: 「クローズグリップを畳むと三頭の種目が胸として提案される」（判断の根拠）
- 残す: 「dependency-cruiser 18.2.0 は TS 7 で 0 モジュールしか走査せず緑になる」（バージョン付きの事実）
- 削る: 「当初はこう書いていたが書き換えた」（推敲の履歴）

外部ツールやライブラリの制約を根拠にするときは、**必ずバージョンを添える。**
状況が変われば見直せるようにするため。

## テンプレート

```markdown
# ADR NNNN: <決定を一文で>

- ステータス: **Draft**
- 日付: YYYY-MM-DD
- 関連: design.md §X.Y

## 背景

何が問題で、なぜ決める必要があるのか。
決めなかった場合に何が起きるかまで書く。

## 決定（案）

何をどう決めるか。

## 理由

なぜその選択なのか。他の選択肢を落とした理由も含む。

## 影響

この決定によって何が変わるか。他の箇所に波及する制約。

## 未解決

この ADR では決めきれなかったこと。次にどの情報があれば決まるか。
```
