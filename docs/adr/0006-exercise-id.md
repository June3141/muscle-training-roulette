# ADR 0006: 種目 id は独自に振り、器具名を含めない

- ステータス: **Proposed**（M1 の写像作業の前に確定させる）
- 日付: 2026-08-17
- 関連: design.md §4.2, ADR 0002

## 背景

種目 id はデータセットの主キーであり、**変えると全件を書き直すことになる。**
M1 の写像作業で id を振るので、その前に決める必要がある。

上流 free-exercise-db の id は英語名のスラグで、大文字とハイフンが混在する。

```
3_4_Sit-Up
Barbell_Bench_Press_-_Medium_Grip
```

873 件で重複はない（`docs/data-survey.md`）。

## 決定（案）

**独自 id を振り、`sourceId` に上流の id を保持する。id に器具名は含めない。**

### 形式

`snake_case` の英数字のみ（スキーマの正規表現で強制済み）。

```
[修飾]_[動作]
```

| 含める | 含めない |
|---|---|
| 角度（`incline_` / `decline_`） | **器具**（`barbell_` / `dumbbell_`） |
| グリップ（`close_grip_` / `wide_grip_`） | **片手/両手**（`one_arm_`） |
| 姿勢（`seated_` / `standing_` / `lying_`） | |

### 例

```
bench_press              ← バーベル/ダンベル/マシン/スミスを equipmentOptions で持つ
incline_bench_press
decline_bench_press
close_grip_bench_press   ← 主働筋が三頭に変わるので別種目（ADR 0002）
lateral_raise
seated_shoulder_press
```

## 理由

### なぜ独自 id を振るのか

上流の id は URL やファイル名として扱いにくく（大文字・ハイフン混在）、
独自種目を追加したときに形式が揃わない。

ただし独自 id **だけ**にすると上流の更新に追随できなくなるので、
`sourceId` に上流の id を残す。両方持てば、上流が種目を追加・修正したときに突合できる。

### なぜ器具名を含めないのか

**ADR 0002 で器具を独立軸にしたため。**
`barbell_bench_press` と `dumbbell_bench_press` を別 id にすると、
統合後の 1 レコードに 2 つの id 候補が生まれて矛盾する。

同じ理由で片手/両手も含めない（`lateralityOptions` の軸なので）。

### なぜ角度とグリップは含めるのか

**これらは別種目として扱うため**（ADR 0002）。
クローズグリップベンチは主働筋が三頭に変わるので、フラットベンチとは別レコードになる。
別レコードである以上、id で区別できなければならない。

## 例外: 器具が動作を規定する場合

器具を変えると動作そのものが変わる種目は、器具名を含めてよい。

```
cable_crossover     ← ケーブル特有の軌道。ダンベルフライとは可動域が違う
smith_machine_row   ← 軌道が固定される
```

判断基準は ADR 0002 と同じ。**主働筋が入れ替わるか、`movementPattern` が変わるなら別種目**で、
その場合は器具名が id に入っても構わない。

## 影響

- M1 の写像作業では、統合後の種目に対して id を振る（統合前の 873 件に振るのではない）
- `sourceId` は 1 対 1 で持てない場合がある。**複数の上流種目を 1 つに畳むため**
  （バーベルベンチとダンベルベンチが 1 レコードになる）。
  スキーマの `sourceId: z.string().nullable()` を配列に変える必要があるかもしれない

## 未解決

- **`sourceId` を配列にするか。** 統合すると 1 レコードが複数の上流 id を持つ。
  現在のスキーマは単数なので、M1 の統合作業に入る前に決める
- 独自種目（上流に存在しないもの）を追加したときの `sourceId` は `null`。
  これは決定済みだが、独自種目であることを別フラグで示すかは未定
